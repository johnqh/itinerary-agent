# Building a trip planner that writes its own scheduler

*A build log from the Agent Harness Hackathon.*

> Written partway through the day. It covers the design and the first failures;
> routing, nearby restaurant search, photograph lookup and the scheduler's
> retry loop came afterwards. For how the finished system works, see
> [how-it-works.md](how-it-works.md).

The brief was to build an agent that does work rather than answers questions,
using [TrueForge](https://github.com/truefoundry/trueforge). We built a trip
planner: give it a city and some dates, it researches what is worth seeing,
stops so you can say what interests you, and then schedules your days.

The interesting part is the last step, and it is the reason we picked this
problem. Scheduling a trip is a time-windowed routing problem — attractions have
opening hours, travel between them takes time, meals happen in windows, and a
rental car changes every leg of a day. That is exactly the kind of problem
language models are bad at and code is good at.

## The one design decision everything else follows from

**Subagents fan out on I/O. The sandbox centralises the math.**

Research is embarrassingly parallel and context-heavy: a dozen attractions, each
needing coordinates, opening hours for specific dates, ticket rules and a
source. That is what subagents are for, and the harness spawns them dynamically
— you enable `dynamicSubAgents` and describe the work, and the orchestrator
decides how many researchers it needs.

Scheduling is the opposite. Day assignment is a *global* decision: independent
per-day planners would double-book attractions and produce geographically
incoherent days. So the agent does not fan out to schedule. It writes a Python
solver, runs it in the sandbox, reads the objective, and iterates when a day
comes back infeasible.

We were surprised how much this simplified the prompt. We do not ask for an
itinerary at all. We hand over coordinates and rules and ask for a program.
Distances are computed in the sandbox rather than in a model's head, which
keeps the payload small and puts the arithmetic somewhere it can be checked.

## Three things only a real run tells you

**Deltas are not the answer.** Our first working discovery run accumulated
`model.message.delta` events into a string, which is the obvious thing to do.
It produced 2,235 deltas of well-written commentary and no usable JSON. The
deltas carry *every thread's* narration, including each subagent's. The
structured answer lives in the terminal `turn.done` state. This would have
shipped silently: the code ran, no error was raised, the output was simply
wrong.

**Strict schemas mean strict.** Our first live turn died on
`Invalid schema for response_format`. In OpenAI's strict mode, `required` must
list *every* key in `properties` — an optional field is expressed as a nullable
type, not an absent one. The harness had the exact explanation in
`state.message`, and our error handling was throwing it away and reporting only
the status. Surfacing the underlying message turned a five-minute mystery into
a one-line fix.

**Progress bars lie by default.** We first reported progress as completed
subagents over spawned subagents. A real run spawned three researchers and made
seventy tool calls, so for most of its life the bar read "0 of 3" while the run
was nearly done. Progress is now fixed stages, with the counters in the label
where they inform without pretending to be a denominator.

## Trusting the agent's output exactly as far as you can check it

The solver's output is code-generated by a model, so it is validated before it
reaches the screen. The validator enforces the rules that decide whether a day
can be walked at all:

- every item inside the day window, in chronological order
- no attraction scheduled twice across the trip, or while it is closed
- no transit leg with a transfer
- no car day that also uses transit
- **every gap between two stops long enough to hold the journey between them**

That last one is the one to watch. It is the easiest constraint to violate and
the hardest to notice: a schedule that ignores travel time looks completely
normal until you try to follow it. Our own greedy planner had this bug, and a
reviewer caught it before we did.

When validation fails, the deterministic planner answers instead and the
traveller is told that happened. A rejected schedule is a worse itinerary; a
silently accepted broken one is a wrong answer.

## Honesty as a design constraint

The rule we kept coming back to: **never invent a fact, and never degrade
silently.**

An opening time the agent could not confirm stays `unknown` — it is not filled
in with something plausible, because a guessed closing time sends someone to a
locked door. With no routing provider connected, transit is reported
unavailable rather than given an invented line and transfer count. Travel times
derived from straight-line distance are labelled estimates everywhere they
appear.

And every fallback names itself on screen: offline data instead of live
research, the greedy planner instead of the sandbox, a meal that could not be
seated, a map tile server that failed. A fallback the user cannot see is
indistinguishable from a bug.

## What went wrong

**Live research is slow.** A thorough run takes seven to thirteen minutes and
seventy-plus tool calls. That is fine for planning a real trip and far too slow
for a demo, so live research became an explicit opt-in and the offline dataset
became the default. Both are labelled.

**We ran out of credit mid-solve.** The optimizer provisioned its sandbox and
ran the solver four times — exactly the iterate-until-feasible loop we wanted to
demonstrate — then hit the organisation's spend limit. The loop works; we have
not yet watched it finish. Saying so is more useful than a green checkmark we
did not earn.

**A global gitignore ate our dataset.** A bare `data` pattern in a personal
global gitignore silently excluded `src/data/`. Everything passed locally
because everything was checked against the working tree. The pushed branch could
not build. The lesson was cheap and worth it: verify against what is committed,
not what is on your disk. The reviewer that caught it earned its keep in one
finding.

## What we would do next

Connect a routing provider. The no-transfer transit rule is implemented and
tested, but with no routing data transit is always unavailable, so the rule
never fires and every non-walking leg is a rideshare. It is the clearest gap
between what the planner can express and what it currently shows.

After that, the harness-native `ask_user_question` suspension, so the rating
step is a real mid-turn pause rather than a boundary between two turns.
